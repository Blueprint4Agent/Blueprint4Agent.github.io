# Admin & roles

Users have one of three roles: `user`, `manager`, or `admin`. Managers and admins can read the user directory at `/admin`; only admins can read the server status at `/admin/server`. Roles are changed by an operator command, not through the UI or an HTTP API.

|               |                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------- |
| **Enable**    | Always available to users with the `manager` or `admin` role                                         |
| **Endpoints** | `GET /api/v1/auth/admin/users`, `GET /api/v1/auth/admin/user-role-stats`, `GET /api/v1/admin/status` |
| **Frontend**  | **Admin panel** in the profile menu (`/admin`, `/admin/server`, `/admin/inquiries`)                  |
| **Command**   | `make user-role EMAIL=<address> ROLE=admin\|manager\|user`                                           |

## Permissions

| Permission                                      | User | Manager | Admin |
| ----------------------------------------------- | ---- | ------- | ----- |
| Own account, API keys, and billing              | Yes  | Yes     | Yes   |
| Read the user directory and role statistics     | No   | Yes     | Yes   |
| Read server status and admin-only endpoints     | No   | No      | Yes   |
| Read, reply to, and close all support inquiries | No   | No      | Yes   |
| Read other users' notifications                 | No   | No      | No    |
| Change another user's role, profile, or billing | No   | No      | No    |
| Inspect or retry other users' lifecycle mail    | No   | No      | No    |

Role changes and failed-mail recovery are operator commands, not role permissions. Roles are explicit allowlists, not an inheritance chain. Managers do not get admin-only access automatically, and new admin endpoints must opt in to each role. Every check reads the current database role, so a role change applies on the next request without reissuing tokens. API keys act as their owner and pass the same role checks.

## Assigning roles

```bash
make user-role EMAIL=operator@example.com ROLE=admin
make user-role EMAIL=manager@example.com ROLE=manager
make user-role EMAIL=manager@example.com ROLE=user
```

The command uses the backend environment (`src/backend/.env`). In a Docker deployment, run it inside the app container:

```bash
cd docker
docker compose exec app .venv/bin/python -m app.manage_user_role --email person@example.com --role admin
```

- Provision the first admin from a normally registered or OAuth account. The command changes existing, active accounts only.
- The last active admin cannot be demoted to `manager` or `user`, or deleted.
- It requires `LOGIN_ENABLED=true`.
- It runs as a standalone process; the server does not need to be running.
- The open browser refreshes navigation after the account data is reloaded.

## Role change audit

Every effective role change writes a `role_change_audit` row in the same transaction: target user ID, old and new role, UTC time, and the operator's OS username (`cli:<name>`). No-op assignments are not recorded. The rows contain no email or credentials and survive account deletion.

This is a trusted-operator record, not tamper-proof auditing. There is no endpoint to read it; control access and retention through database operations.

The audit table is created by migration `0010_role_change_audit`, which the app applies on startup.

## User directory

The panel at `/admin` reuses the settings layout. A summary shows four role and account counts (two columns on mobile), and the table lists each user's name, email, role, account and verification status, login methods, signup date, and latest successful login.

- Search by name or email, filter by role and by enabled/disabled status.
- Results are paginated (`page_size` 1–100, default 20), newest first.
- **Active** means the account is enabled, not that the user is online.
- IP addresses, user agents, passwords, tokens, and provider identifiers are never returned.

The panel refreshes on focus, visibility, manual refresh, and connectivity recovery. It does not poll or stream user changes.

## Server status \{#server-status\}

`/admin/server` is a read-only, admin-only snapshot of the running server. Managers cannot open it.

| Row            | Shows                                                                                                                           |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Database       | Dialect, hostname and port, status, latency. SQLite is labeled as a local file.                                                 |
| Redis          | Hostname and port, or in-memory, with status and latency                                                                        |
| Object storage | Local, Amazon S3, Cloudflare R2, or Supabase, with transport, port, status, and latency                                         |
| Email, Stripe  | Current connectivity: SMTP connection and authentication, and a read-only Stripe call. No email or billing resource is created. |
| Startup checks | The results recorded when the process started, with their original timestamp                                                    |
| Environment    | Effective email, login, OAuth, billing, development UI, and runtime mode values                                                 |

- Database and Redis checks run concurrently with 2-second timeouts, shared with `/health/ready`.
- Email, Stripe, and storage checks are cached per process for 60 seconds, shared between concurrent requests, and wait at most 5 seconds.
- The page refreshes every 30 seconds while visible and on focus or reconnection. A failed refresh or a snapshot older than 60 seconds is marked stale.
- OAuth has no health badge: configuration cannot prove a successful user sign-in.
- Connection URLs, credentials, database names, bucket names, endpoints, regions, and local paths are never returned.

A storage check proves bucket access only, not upload permission or bucket privacy. Worker health and historical metrics are outside this snapshot.

## Admin demo \{#admin-demo\}

With `DEMO_ENABLED=true`, any visitor, including guests, can open a read-only copy of the admin panel built from real but anonymized data. It is off by default, works in both runtime modes, and needs no frontend rebuild.

| Route                   | Data source                     | Shows                                                  |
| ----------------------- | ------------------------------- | ------------------------------------------------------ |
| `/demo/admin`           | `GET /api/v1/admin/demo/users`  | The user directory with pseudonymized identities       |
| `/demo/admin/server`    | `GET /api/v1/admin/demo/status` | Real server health with connection addresses removed   |
| `/demo/admin/inquiries` | None (bundled sample data)      | The support screen with synthetic, localized inquiries |

- The entry is **Admin panel (demo)** in the profile menu, and the home previews link to it. Real admins see only their normal **Admin panel**. `/config` reports `demo_enabled`.
- The demo APIs reuse the admin response schemas and are GET-only. Real admin routes keep their role checks, and nothing can be changed from the demo.
- **Published:** totals, roles, active and verified flags, login provider names, UTC signup and last-login dates (day only), and server health with effective feature flags.
- **Replaced or removed:** names, emails, and database IDs become keyed pseudonyms, and search matches pseudonyms only. Internal hosts and ports are removed. Credentials, IP addresses, profile data, and support messages are never exposed.
- Snapshots are coalesced and cached per process for up to 30 seconds, and errors fail closed. The first directory snapshot reads a minimal projection of every user, so check memory on large installations.
- Pseudonyms are keyed by `SECRET_KEY`. Do not rotate it just to change aliases, because it also signs tokens.
- Pseudonymization does not prevent inference in small user bases. Setting `DEMO_ENABLED=false` and redeploying removes the entry, and the demo APIs return 404.

The demo does not enable metrics, tracing, or log export.

## Support inquiries

`/admin/inquiries` lists every [support inquiry](/docs/features/support) with a status filter. Admins reply and set **Open**, **In progress**, or **Closed**. Managers see only their own inquiries in Settings.
