# Home, settings & profile

B4React ships a complete app shell: a landing home page, three deployment layouts, a settings workspace, account and profile editing, light and dark themes, customizable keyboard shortcuts, and toast feedback.

## Home

`/home` is the default page in both [runtime modes](/docs/environment/runtime-modes). `/`, `/dashboard`, login completion, closing an auth dialog, and page recovery all lead there. It is a product landing page that works in every [layout](#layouts):

| Section       | Contents                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------- |
| Introduction  | Headline, GitHub and User guide links, and a product preview beside it (stacked on narrow screens) |
| Preview       | Real screenshots with demo data: Users, Server status, Billing, and Showcase                       |
| Features      | Cards grouped into _For your users_, _Inside the product_, and _Behind the scenes_                 |
| Workflow      | Three numbered steps: set up, build, verify and deploy                                             |
| Use cases     | Subscription services, internal tools, customer portals, and product prototypes                    |
| Account links | Quick links filtered by sign-in state and role                                                     |
| Footer        | Product, resource, and account columns that reuse the same destinations and role checks            |

- **Section links** jump to Preview, Features, Workflow, and Use cases. Top-navigation and minimal layouts center them in the header; the sidebar layout shows a floating capsule. Scrolling is smooth unless reduced motion is requested.
- **Previews** crossfade every six seconds with a progress line, including while hovered or focused. An explicit pause, the enlarged viewer, an offscreen or hidden tab, and reduced motion stop rotation. **Open screen** follows the existing role checks.
- Screenshots contain fictional data, never real accounts or server health, and the feature list describes what the blueprint supports, not what is currently enabled.

| Viewer         | Account links                                                                     |
| -------------- | --------------------------------------------------------------------------------- |
| Guest          | A **Log in** entry, Account (to `/login`), Billing (to `/plans`), and Preferences |
| Signed-in user | Account, Billing, Notifications, Support, and Preferences                         |
| Manager, admin | An additional User directory link                                                 |

Billing links appear only when billing is enabled. Guests trigger no private API requests.

`MainPageTemplate` in `src/components/layout` remains the presentational layout for settings-style menu pages you add to the product:

| Prop                           | Purpose                                                        |
| ------------------------------ | -------------------------------------------------------------- |
| `title`, `description`, `icon` | Heading content                                                |
| `actions`                      | Header controls composed from existing components              |
| `menuLabel`, `menuItems`       | Accessible navigation with IDs, routes, titles, and icons      |
| `menuLayout`                   | `list` (default) or responsive `grid`                          |
| `children`                     | Additional sections, lists, cards, or loading and empty states |

The template owns no auth, API, routing state, or storage. The owning page filters items by permission and fetches its own data through hooks.

## App shell

- The sidebar layout: 48px collapsed, 224px expanded, resizable from 200 to 360px. The width is remembered.
- The profile control and connectivity status stay available in every layout. In development mode, GitHub, User guide, and the optional support link sit beside them.
- With billing enabled, the profile shows the subscription tier, and the profile menu opens `/plans`.
- The profile menu holds **Profile**, **Notifications** directly below it with an unread badge (see [Notification inbox](/docs/features/notifications)), and **Admin panel** for managers and admins. When the [admin demo](/docs/features/admin-and-roles#admin-demo) is on, other visitors, including guests, see **Admin panel (demo)** instead.
- On mobile the sidebar overlays content with a dismissible backdrop.
- When the server is unreachable, the recovery panel stays inside the same layout.

## Layouts \{#layouts\}

| `APP_LAYOUT`        | Shell                                                                                      |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `sidebar` (default) | Collapsible, resizable left rail                                                           |
| `topnav`            | Global navigation in a horizontal header; narrow screens use a menu icon left of the brand |
| `focused` (Minimal) | Compact transparent header; a menu icon left of the brand opens a small navigation popup   |

- The deployment chooses the layout with the runtime setting `APP_LAYOUT`, exposed as `app_layout` in `GET /config`. The same image serves all three: recreate the container with a new value and reload the browser. An unknown value fails startup validation. `src/service.config.ts` is only a fallback for providers that do not send the field.
- Global navigation contains Home and, in development, the showcase. It never contains Settings or admin section lists: without the sidebar, those sections use a boxed column beside the content, which becomes a disclosure above it on narrow screens.
- Home, profile, inbox, error, and auth pages keep their own page styles. `/plans` and the public `/about/` pages keep their independent shells.
- When the server reports `app_mode=development`, **Settings → Appearance → Layout** previews another layout in this browser only, and that preview takes precedence over `APP_LAYOUT`. **Use service default** removes it. Production ignores saved previews and hides the selector. Open clients pick up a changed `APP_LAYOUT` on reload.

## Settings sections

| Section    | Who                                    | Contents                                                                                         |
| ---------- | -------------------------------------- | ------------------------------------------------------------------------------------------------ |
| General    | Everyone                               | Language (English, Korean)                                                                       |
| Appearance | Everyone                               | System, light, or dark theme with previews; layout preview in development                        |
| Keyboard   | Everyone (editing for signed-in users) | Shortcut bindings                                                                                |
| Account    | Signed-in users                        | Name, email, linked login methods, plan, password change, account deletion                       |
| Billing    | Signed-in users, billing enabled       | Plan, transactions, billing information, payment methods. See [Billing](/docs/features/billing). |
| Support    | Signed-in users                        | Private [support inquiries](/docs/features/support) and their replies                            |
| Developers | Signed-in users                        | [API keys](/docs/features/api-keys)                                                              |

The section is part of the URL (`/settings?section=...`); the legacy `section=profile` opens Account. Guests are redirected to General when they open an account-only section, and Billing falls back to General when billing is off.

## Account

**Settings → Account** holds identity and security:

- **Name**, edited inline; saves confirm with a toast and errors stay beside the field.
- **Email**, connected sign-in providers, signup date, and the current plan.
- **Change password**, in a modal that sends a six-digit code to the registered email. See [Authentication](/docs/features/authentication#password-change).
- **Delete account**, in a separate section at the bottom, with the same email-code modal. See [Authentication](/docs/features/authentication#account-deletion).
- **Go to profile**, which opens the profile page.

With `EMAIL_ENABLED=false`, password change and account deletion are disabled with an explanation; they never skip the email proof.

## Profile \{#profile\}

`/profile` is a private page for the signed-in user. It opens from the sidebar profile menu, the Account section, or <kbd>Mod</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd>, inside the same sidebar layout the user came from. There is no public profile and no way to view another user's profile.

| Field           | Rule                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| Photo           | Managed upload, saved immediately. See [Object storage](/docs/features/object-storage#profile-photos). |
| Name            | Required                                                                                               |
| Bio             | Optional, up to 100 characters; line breaks are kept                                                   |
| Country, region | Optional linked dropdowns from a pinned catalog (249 countries, 4,387 subdivisions); never geolocation |
| Signup date     | Read-only                                                                                              |
| Current plan    | From the shared subscription snapshot; Free when billing is off                                        |

- Name, Bio, and location can be edited in place on the page, or together in an edit modal. Each inline save patches only that field, and a failed save keeps the draft. Clicking outside an inline editor cancels its draft; the save button and floating menus such as the location dropdown do not.
- `GET/PATCH /api/v1/auth/me` stays the single source of truth: `bio` and `location` are cleared with `null` and kept when omitted. The backend validates the same country and region pairs as the UI.
- Saved changes update the sidebar at once. Other open clients see them after their next reload or sign-in.
- The page enters with the shared rise animation and honors reduced motion.

## Keyboard shortcuts

| Action             | Default                                                            |
| ------------------ | ------------------------------------------------------------------ |
| Toggle the sidebar | <kbd>Mod</kbd> + <kbd>B</kbd>                                      |
| Open settings      | <kbd>Mod</kbd> + <kbd>,</kbd>                                      |
| Open profile       | <kbd>Mod</kbd> + <kbd>Shift</kbd> + <kbd>P</kbd> (signed-in users) |

<kbd>Mod</kbd> is Command on macOS and Control on Windows and Linux.

Bindings are stored in the account (`keyboard_shortcuts` on `GET/PATCH /auth/me`), so they follow the user across browsers and devices. Guests see the defaults read-only. The profile shortcut is ignored while typing in a field or when a dialog is open. Conflicting bindings are rejected, only confirmed saves replace the active keys, and **Reset** restores the defaults. Changes appear in other open clients after a reload or sign-in.

## Toasts and feedback

Explicit actions confirm once with a short capsule toast at the top of the screen: sign-in and sign-out, signup, verification resend, password reset, profile changes, API key actions, billing confirmations, and copying secrets. Validation errors stay inline, persistent notices use `InlineMessage`, and toasts never contain passwords, secrets, or tokens.

## Localization

All UI text is translated into English and Korean with react-i18next. Emails follow the user's language.
