# 관리자와 역할

사용자는 `user`, `manager`, `admin` 중 하나의 역할을 가집니다. 매니저와 관리자는 `/admin`에서 사용자 목록을 볼 수 있고, 서버 상태(`/admin/server`)는 관리자만 볼 수 있습니다. 역할은 UI나 HTTP API가 아닌 운영자 명령으로 변경합니다.

|                |                                                                                                      |
| -------------- | ---------------------------------------------------------------------------------------------------- |
| **활성화**     | `manager` 또는 `admin` 역할 사용자에게 항상 제공                                                     |
| **엔드포인트** | `GET /api/v1/auth/admin/users`, `GET /api/v1/auth/admin/user-role-stats`, `GET /api/v1/admin/status` |
| **프론트엔드** | 프로필 메뉴의 **관리자 패널**(`/admin`, `/admin/server`)                                             |
| **명령**       | `make user-role EMAIL=<address> ROLE=admin\|manager\|user`                                           |

## 권한

| 권한                                    | User   | Manager | Admin  |
| --------------------------------------- | ------ | ------- | ------ |
| 본인 계정, API 키, 결제                 | 예     | 예      | 예     |
| 사용자 목록과 역할 통계 조회            | 아니요 | 예      | 예     |
| 서버 상태와 관리자 전용 엔드포인트 조회 | 아니요 | 아니요  | 예     |
| 다른 사용자의 역할·프로필·결제 변경     | 아니요 | 아니요  | 아니요 |

역할은 상속 구조가 아닌 명시적 허용 목록입니다. 매니저는 관리자 전용 권한을 자동으로 얻지 않으며, 새 관리자 엔드포인트는 역할별로 명시적으로 허용해야 합니다. 모든 검사는 현재 데이터베이스의 역할을 읽으므로 토큰을 다시 발급하지 않아도 다음 요청부터 변경된 역할이 적용됩니다. API 키는 소유자 권한으로 동작하며 같은 역할 검사를 거칩니다.

## 역할 지정

```bash
make user-role EMAIL=operator@example.com ROLE=admin
make user-role EMAIL=manager@example.com ROLE=manager
make user-role EMAIL=manager@example.com ROLE=user
```

이 명령은 백엔드 환경(`src/backend/.env`)을 사용합니다. Docker 배포에서는 앱 컨테이너 안에서 실행합니다.

```bash
cd docker
docker compose exec app .venv/bin/python -m app.manage_user_role --email person@example.com --role admin
```

- 첫 관리자는 일반 가입 또는 OAuth로 만든 계정에 지정합니다. 이미 있는 활성 계정만 변경합니다.
- 마지막 활성 관리자는 `manager`나 `user`로 강등하거나 삭제할 수 없습니다.
- `LOGIN_ENABLED=true`가 필요합니다.
- 독립 프로세스로 실행되므로 서버가 실행 중이지 않아도 됩니다.
- 열려 있는 브라우저는 계정 정보를 다시 불러온 뒤 메뉴를 갱신합니다.

## 역할 변경 감사 기록

실제로 역할이 바뀔 때마다 같은 트랜잭션에서 `role_change_audit` 행을 기록합니다. 대상 사용자 ID, 이전·새 역할, UTC 시각, 운영자의 OS 사용자 이름(`cli:<name>`)이 저장됩니다. 변경이 없는 지정은 기록하지 않습니다. 이메일이나 자격 증명은 포함하지 않으며 계정 삭제 후에도 유지됩니다.

신뢰할 수 있는 운영자 기록이며 변조 방지 감사 로그는 아닙니다. 조회 엔드포인트는 없으며, 접근 권한과 보존 기간은 데이터베이스 운영으로 관리합니다.

감사 테이블은 앱 시작 시 적용되는 마이그레이션 `0010_role_change_audit`이 만듭니다.

## 사용자 목록

`/admin` 패널은 설정 레이아웃을 재사용합니다. 상단 요약에 역할·계정 수 네 가지(모바일은 두 열)를 보여주고, 표에는 사용자마다 이름, 이메일, 역할, 계정·인증 상태, 로그인 방식, 가입일, 마지막 로그인 성공 시각을 보여줍니다.

- 이름이나 이메일로 검색하고, 역할과 활성·비활성 상태로 필터링합니다.
- 결과는 최신순으로 페이지네이션됩니다(`page_size` 1–100, 기본 20).
- **활성**은 계정이 사용 가능하다는 뜻이며 현재 접속 중이라는 뜻이 아닙니다.
- IP 주소, user agent, 비밀번호, 토큰, 제공자 식별자는 반환하지 않습니다.

패널은 포커스, 화면 표시, 수동 새로고침, 연결 복구 시 갱신됩니다. 사용자 변경을 폴링하거나 스트리밍하지 않습니다.

## 서버 상태

`/admin/server`는 실행 중인 서버의 읽기 전용 스냅샷이며 관리자만 볼 수 있습니다. 매니저는 열 수 없습니다.

| 행                | 표시 내용                                                                                    |
| ----------------- | -------------------------------------------------------------------------------------------- |
| 데이터베이스      | 방언, 호스트 이름과 포트, 상태, 지연 시간. SQLite는 로컬 파일로 표시                         |
| Redis             | 호스트 이름과 포트 또는 인메모리, 상태와 지연 시간                                           |
| 오브젝트 스토리지 | Local, Amazon S3, Cloudflare R2, Supabase와 전송 방식, 포트, 상태, 지연 시간                 |
| 이메일, Stripe    | 현재 연결 상태: SMTP 연결·인증과 읽기 전용 Stripe 호출. 이메일이나 결제 리소스를 만들지 않음 |
| 시작 검사         | 프로세스 시작 시 기록된 결과와 원래 시각                                                     |
| 환경              | 실제 적용된 이메일, 로그인, OAuth, 결제, 개발 UI, 런타임 모드 값                             |

- 데이터베이스와 Redis 검사는 `/health/ready`와 같은 2초 제한으로 동시에 실행됩니다.
- 이메일, Stripe, 스토리지 검사는 프로세스별로 60초 동안 캐시되고 동시 요청이 공유하며 최대 5초까지 기다립니다.
- 화면이 보이는 동안 30초마다, 그리고 포커스·재연결 시 갱신됩니다. 갱신에 실패하거나 60초보다 오래된 스냅샷은 오래된 정보로 표시됩니다.
- OAuth는 설정만으로 실제 사용자 로그인 성공을 증명할 수 없으므로 상태 배지가 없습니다.
- 연결 URL, 자격 증명, 데이터베이스 이름, 버킷 이름, 엔드포인트, 리전, 로컬 경로는 반환하지 않습니다.

스토리지 검사는 버킷 접근만 확인하며 업로드 권한이나 버킷 공개 여부는 확인하지 않습니다. 워커 상태와 과거 지표는 이 스냅샷에 포함되지 않습니다.
